Архитектура Pinega Engine

Эта страница объясняет принятые архитектурные границы. Это не руководство по установке и не утверждение, что каждый механизм уже реализован или измерен.

Целевая граница: PostgreSQL 19, направление Table Access Method только в расширении, без необходимости изменять ядро для текущей программы движка.

Интеграция с PostgreSQL

Pinega Engine проектируется для подключения через API расширений PostgreSQL, прежде всего через границу Table Access Method. PostgreSQL отвечает за видимую из SQL идентичность транзакций, снимки и окружающую интеграцию с исполнителем и каталогом. На стороне расширения нужен узкий явный C ABI вокруг взаимодействий Rust/pgrx и pg_sys.

Изменяемое хранилище версий

Путь OLTP использует версии строк с размещением вне исходного положения в постоянных файлах Pinega, а не блоки кучи PostgreSQL. Метаданные видимости явны, чтобы оценку версий, дескрипторы и будущую SIMD-обработку можно было строить вокруг собственного представления движка.

Неизменяемое аналитическое направление на основе Vortex — более поздний уровень программы и не смешивается с минимально жизнеспособной версией OLTP.

Собственный общий буферный пул Pinega

Поскольку изменяемое хранилище использует собственные постоянные файлы, а не блоки PostgreSQL, Pinega владеет соответствующим буферным пулом в общей памяти. Исследовательское направление включает стабильные фреймы, дескрипторы поколений и версий, защиту или фиксацию с повторной проверкой, явный вывод из обращения и рекламацию, а также размещение с учётом кешей, когерентности и NUMA.

Механизмы без блокировок и ожидания являются целями исследования и реализации, а не общим заявлением, будто производственный менеджер буферов уже обеспечивает такие гарантии прогресса.

Долговечность: единый PostgreSQL WAL

Принятое решение

PostgreSQL WAL остаётся единственным журналом предзаписи и границей фиксации. Минимально жизнеспособная версия может журналировать полные образы кортежей; логическая репликация входит в область работ, а физический резервный сервер, агрессивная сборка мусора и повторное использование пространства могут последовать после проверки основного пути.

Так внутри расширения не возникает второй независимый протокол фиксации, подобный WAL и случайно превращающийся в задачу распределённой долговечности.

Архитектура не является доказательством производительности

Архитектура предлагает механизмы для улучшения OLTP и явного управления временем жизни конкурентных объектов. Заявления о производительности, масштабируемости, crash safety и совместимости с PostgreSQL требуют реализации, бенчмарков и доказательств корректности.

Портфельный обзор находится в разделе «Технологии», а активные вопросы и доказательства — в каталоге исследований.
